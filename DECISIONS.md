# Resolved Decisions

Resolves the `[DECIDE]` items from Section 14 (and inline callouts) of `gaskiya-hackathon-spec.md`. Treat this as authoritative over the spec's suggestions where they differ.

| Decision | Resolution |
|---|---|
| Corroboration threshold N for `community_verified` | **3** independent corroborations |
| Report threshold N for auto-`flagged` | **5** community reports (admin-adjudicated below that) |
| Hand-roll B-tree vs. native DB index | **Native DB (Postgres) B-tree index.** Hand-rolled effort goes entirely into the Merkle hash-chaining and Cuckoo shard-assignment modules — those are the actual research differentiator; B-trees are well-understood and Postgres's indexes are genuinely B-trees, so the claim in Section 9 holds without hand-rolling. |
| Backend/frontend stack | **Rust (Actix web) backend + Next.js/TypeScript frontend**, per the spec's suggested stack (Section 9). Engine logic (`/engine`: Merkle chaining, Cuckoo hashing, proof generation) built as a standalone Rust module, independent of the web framework. |
| PWA installability (manifest + service worker) | **Stretch goal, not core.** Build only after the non-negotiable MVP (hash-chained versioning, history timeline UI, one pivot-detection example, verify button) and the rest of the build order (Section 10) are done with time to spare. |
| Project name/branding | **Keep "Gaskiya."** |
| Database | **PostgreSQL**, accessed via `sqlx` from the Rust backend, run locally through `docker-compose`. Chosen over SQLite for parity with the Railway/Render deploy target and because its native B-tree indexes back the "B-tree indexed search layer" claim directly. |

## Rationale notes (B-tree decision)

Considered hand-rolling a fully custom Merkle-hashed, append-only B-tree (closer to a persistent Merkle trie than a textbook B-tree, given the versioning requirement). Estimated cost: ~1–2 days for a robust version, 6–8 rushed hours for a version likely to carry balancing bugs. That time directly competes with the Cuckoo hashing, trust-scoring engine, IPFS anchoring, and frontend work, which are higher-priority per the spec's own build order and success criteria. A native DB index also better supports the multi-field search API (`category` + `region` + `deadline_before` + `status`) than a single hand-rolled B-tree would without extra secondary-index work. Decision: rely on Postgres's native B-tree index; concentrate hand-rolled work on Merkle + Cuckoo.

## Fit against the hackathon's stated project scope

The brief requires the project to "do more than present information" and "help people improve how they engage with governments and public services." Gaskiya already has two-way mechanics beyond passive browsing (citizens corroborate/report, institutions sign and publish directly through the platform), but as scoped it still hands a citizen off to an external `application_url` rather than participating in their actual engagement with the institution. Resolution: add a **watchlist** (implemented — see below) so the platform stays involved through the citizen's own application process, not just at discovery. This directly reuses the existing trust-lifecycle machinery (a status change while watched is the same signal the history-timeline/pivot-detection feature already surfaces) rather than adding a disconnected feature.

## Operating constraints — how each maps onto the architecture

The brief also lists conditions the solution must account for. Mapping each to a concrete decision, so later phases (trust engine, frontend, AI-assist) inherit the right defaults instead of re-deriving them:

| Constraint | Decision |
|---|---|
| **Trust & verification** — must be traceable, and users must know when it last changed | Every listing surfaces `version_created_at` (when content last changed) and `status_computed_at` (when trust status was last recomputed) directly in `/api/search` and `/api/listings/:id` responses — not buried in the history view. The hash chain + Merkle anchor (already built) make "traceable" a cryptographic property, not a policy promise. |
| **Low bandwidth / limited access** | `/api/search` caps results at 100 rows; PWA/offline is already a stretch goal (see table above), not core. Frontend phase should keep payloads lean (avoid shipping full Merkle proofs on list views — only fetch them on the `/verify` detail action) and design for basic devices before richer interactions. |
| **Accessibility & inclusion** | No backend implication yet; a frontend-phase commitment. Plain-language eligibility summaries (spec Section 9 AI-assist) exist specifically to serve lower-literacy and lower-digital-confidence users — treat that as core to the pitch, not a nice-to-have polish item. |
| **Privacy & security** | No auth system exists (citizens are "anonymous or lightly registered," spec Section 4). Adopted a **client-generated opaque UUID as a capability token**: the frontend creates a random UUID once, holds it in `localStorage`, and sends it as `user_id`/`author_id`/`corroborator_id`/`reporter_id`. No email, password, or PII is ever collected. Possession of the UUID is the only access control on endpoints like `GET /api/watchlist/:user_id` — acceptable for a hackathon demo (state this limitation explicitly, same honesty pattern as Section 12), not a substitute for real auth. |
| **Multilingual access** | No schema change: `ListingContent` fields are plain strings, language-agnostic. Translation is an output-layer concern (spec Section 9 AI-assist: "optional translation for demo authenticity") — handle it as a display transform, not stored per-language duplicate rows, to avoid the append-only chain having to reason about which language is "the" content. |
| **Local relevance** | Already modeled: `region` is a free-text field per listing, `eligibility`/`contact` are free text so local institutions/requirements aren't forced into a fixed vocabulary. No change needed. |
| **Clear next steps** | Already modeled, not a new field: `application_url` answers "where do I go," `contact` answers "who do I contact," `eligibility` answers "what do I need." The watchlist closes the remaining gap — "how do I know if something changed after I started" — without adding schema churn. |

## Trust engine (implemented)

`server/src/trust.rs`. A few judgment calls not spelled out in spec Section 6:

- **Institutional signatures are real Ed25519**, not a "field is non-empty" placeholder — verified against a registered public key (`POST /api/institutions`). This matches the project's own anti-overclaiming principle (Section 3): the *identity vetting* is simulated (an allowlist, not KYC), but the *cryptographic check* on top of that allowlist is not.
- **Status stickiness**: once a listing is `flagged` or `confirmed_scam`, it stays there on every future recompute regardless of new corroborations — the lifecycle diagram in Section 6 shows no automatic path back to a positive status, so the rule engine doesn't invent one. `confirmed_scam` is admin-only and never set automatically.
- **"Known scam corpus" (signal 4)** is implemented as the ledger's own prior `flagged`/`confirmed_scam` listings, rather than a separately seeded table — a near-duplicate (Jaccard similarity ≥ 0.8 over word 3-shingles) against any of them is itself a flagged trigger. An exact `content_hash` match against any other listing (a byte-identical clone posted as a new listing rather than a version edit) is also a flagged trigger.
- **Structural red flags (signal 5)**: only the rule-based half is built now (upfront-fee phrase matching escalates to `flagged`; urgency language is recorded but doesn't alone flag a listing, since legitimate deadline-driven programs use similar phrasing). The LLM-assisted pass is deferred to the AI-assist build-order phase, as the spec's own phasing implies.
- **Domain-mismatch check** (claimed institutional affiliation vs. registered domain) is not implemented — the `institutions` table has no domain field. Documented gap, not a silent omission.
- **Score formula** is illustrative, not adversarially tuned (spec Section 12's own caveat): +40 valid signature, +10/corroboration (capped at 3), −15/report, −100 pivot, −60 duplicate, −60 upfront-fee flag, −10 urgency flag, −100 confirmed_scam override. Only `status` drives the badges described in the spec; score is a secondary display number.

## Frontend (implemented)

Next.js (App Router) + TypeScript + Tailwind v4 + shadcn/ui, per the earlier stack decision. A few choices made during the build:

- **Component library**: shadcn/ui, on the `base-nova` style, which is built on **Base UI** (not Radix). Base UI's composition prop is `render={<Element />}` rather than Radix's `asChild` — e.g. `<Button render={<Link href="..." />}>`, with `nativeButton={false}` when the rendered element isn't a real `<button>` (needed for accessibility; Base UI warns in the console otherwise).
- **Data fetching**: plain `useEffect` + `fetch` in client components, not Suspense/`use()`. Next 16's `eslint-config-next` enables React Compiler-readiness lint rules (`react-hooks/set-state-in-effect`, `react-hooks/purity`) as errors by default, which flag this pattern — but the React Compiler itself is off for this project (scaffolded with `--no-react-compiler`), and rearchitecting every page around Suspense-based fetching for a hackathon was judged disproportionate. Downgraded those two rules to warnings in `eslint.config.mjs` with a comment explaining why, rather than silently disabling or leaving a wall of lint errors.
- **CORS**: the backend allows any origin/method/header (`actix-cors`, wide open). Safe here specifically because auth is a bearer-style UUID carried in the request body, not a cookie — there's no session state a permissive CORS policy could leak. Would need tightening before any real deployment.
- **Real in-browser Ed25519**: `@noble/ed25519` (not a Node-only or WASM-only library — it works directly in the browser via Web Crypto for SHA-512 hashing). Verified byte-for-byte interoperable with the Rust `ed25519-dalek` engine both directions before wiring it into the UI: a Rust-generated private key's derived public key matched in JS, and a JS-generated signature verified successfully in Rust (see the interop check performed during the build; not committed as a permanent test since it was a one-time cross-language sanity check, not project behavior). The institution console generates keypairs client-side and only ever sends the public key to the server.
- **Client-side canonical hashing** (`src/lib/canonical.ts`): reimplements the Rust engine's `content_hash` (sorted-key JSON, SHA-256) and `MerkleProof::verify` (hash-pair over concatenated hex-string bytes) exactly in TypeScript, so the "Verify" button performs genuine independent verification rather than displaying the server's own verdict. Deadlines are handled as date-only inputs formatted as `YYYY-MM-DDT00:00:00Z` to match chrono's default serialization exactly (see `dateOnlyToRfc3339`).
- **Shard distribution reset on backend restart**: the Cuckoo table is in-process state, so a server restart used to show an empty dashboard despite historical data in Postgres. Fixed by replaying all existing listing IDs into the table (in original creation order) at startup — deterministic placement means this exactly reconstructs the pre-restart distribution.
- **Browser testing without a display or sudo**: this environment has no GUI, no `chromium-cli`, and no passwordless sudo (so `playwright install --with-deps` can't install OS packages). Worked around by installing Playwright's browser binary directly (no `--with-deps`) and extracting its missing shared libraries (`libnspr4`, `libnss3`, etc.) from the official `mcr.microsoft.com/playwright` Docker image via `docker cp`, then running the host Chromium binary with `LD_LIBRARY_PATH` pointed at the extracted libs. `docker run --network host` was tried first but didn't share the host's network namespace in this sandboxed setup; the `LD_LIBRARY_PATH` approach runs Chromium as a normal host process instead, so it reaches `localhost` directly. Worth capturing as a project skill (`/run-skill-generator`) if browser-driven testing will recur.

## Watchlist feature (implemented)

`watchlist_entries` table + `POST/GET/DELETE /api/watchlist*` (see README for the full route list). A user watches a listing; if its trust status changes before they acknowledge, `GET /api/watchlist/:user_id` reports `status_changed: true` alongside the old and new status. Verified end-to-end, including simulating a phase-4-style status flip via direct SQL (since the trust-scoring rule engine that would normally write that snapshot isn't built yet) and confirming the alert fires, then clears on acknowledge.
